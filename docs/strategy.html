判定策略说明

本文档记录 ModSideDetector 的判定规则，以及开发过程中在真实数据（151 个 NeoForge 1.21.1 模组）上新踩到的坑。HANDOFF.md 记录的是接手前的实测结论， 本文档记录的是实现阶段新增的发现，两者互补，都不要删。

一、判定枚举与置信度

判定 含义 分发含义
client 纯客户端 只发给玩家
server 纯服务端 只放服务器
both 双端 两边都装
unknown 判不了 按 config.unknown_as 处理（默认 both）
置信度 触发条件
high 两源一致；或某源给出明确依据（client_side=unsupported、mcmod 明写「某端无效」、clientSideOnly=true）
medium 只有单一数据源有数据（按需求书：只有一源 → 采信但降置信度）
low 两源冲突；无数据源；弱信号兜底；server 判定被铁律降级

界面高亮规则：conflict=True（两源冲突）与 needs_review=True（需人工确认） 的行必须高亮 —— 这两类才是用户真正需要看的，其余行扫一眼即可。

二、数据源权重

数据源 实测覆盖率 在融合中的角色
mcmod「运行环境」 92%（HANDOFF 实测） 主源之一，有明确单侧依据时权重最高
Modrinth client_side/server_side 120/151 = 79.5%（本项目实测） 主源之一，可批量查询
jar 元数据（clientSideOnly / Fabric environment） 约 6% 显式声明，给 high，但覆盖率低
mixin / data/ 等启发式 100% 覆盖但不准 只作提示，不单独定案
人工复核 100% 永远最高优先级，写进缓存后不再被覆盖

三、融合规则（src/detector.py::merge_verdicts）

文本
人工复核存在                -> 直接采用（confidence=high，manual=True）
─────────────────────────────────────────────────────────────
mcmod 与 Modrinth 都给判定：
    两者相同                -> 采信，high
    两者不同                -> 见下方「冲突处理」
只有一源有判定              -> 采信，medium
两源都没有                  -> 启发式能判就用启发式（low）
                            否则 both（low，needs_review）
─────────────────────────────────────────────────────────────
最后一道闸：side == server 但没有 high/medium 置信度的支持者
                            -> 强制降级 both（needs_review）

冲突处理

冲突时默认不猜谁更权威，保守取 both 并请人工确认 —— 猜错的代价是崩游戏。

唯一例外：mcmod 给出了明确单侧依据（运行环境 里明写「服务端无效」或 「客户端无效」），而 Modrinth 只有弱依据（optional 之类）时，采信 mcmod， 但置信度压到 low 且 needs_review=True，绝不做静默采信。

依据：HANDOFF.md 反复强调 mcmod 质量最高；而 Modrinth 的字段由作者自填、经常不准 （这正是本项目存在的理由）。例外被严格限制在「mcmod 有明确依据」+「Modrinth 依据弱」 两个条件同时成立时。

四、铁律（写在代码里，不是文档里）

铁律 实现位置
绝不允许把「不确定」判成 server detector.merge_verdicts() 最后一道闸
无数据源时默认 both，不是 unknown/server merge_verdicts() 兜底分支
config.unknown_as 只允许 both/unknown config.Config.__post_init__() 强制纠正
一键分类默认只复制不移动 report.classify_copy()
目标同名不同内容绝不覆盖 report.classify_copy()
mcmod 抓取串行限流 ≥0.6 秒/请求 net.RateLimiter + mcmod.McModSource

验收测试：tests/test_core.py::TestMergeRules::test_never_judge_server_without_evidence、 tests/test_accuracy.py::TestAccuracy::test_no_false_server、 tests/test_core.py::TestClassifyCopy。

五、实现阶段新发现的坑（HANDOFF 未记录）

坑 1：mcmod 搜索结果会被「正文提及」污染 ⚠️ 严重

HANDOFF.md 2.1 节给的抓取方式是「搜索页正则 /class/(\d+)\.html → 取第一个」。 实测这是错的。

搜索关键词 sodium 时，搜索页第一条 /class/ 链接是 /class/332.html，标题 [BOT] 植物魔法 (Botania) —— 只因为植物魔法的介绍正文里提到了 "Sodium" 就被召回。 照搬原方案会拿植物魔法的运行环境去判定钠的侧别，产生完全错误的结论。

正确做法（已实现于 src/sources/mcmod.py::_parse_search_results_ex）：

  1. 只认 <div class="result-item"> 里 <div class="head"> 块中的条目标题链接， <div class="body">（正文预览）里的链接一律忽略；
  2. 取出 (classId, 标题) 后，必须用标题与查询名做匹配校验，只接受匹配上的条目；
  3. 一条都不匹配时宁可返回「没找到」，也绝不拿错误条目的运行环境去判定 —— 错误结论比没有结论危害大得多。

坑 2：Modrinth 的 server_side=optional 不是「服务端需要」

初版把 client=required, server=optional 判成了 both，导致 Xaero's Minimap、 Xaero's World Map、Axiom 这类被误判为双端。

optional 的语义是「不装也能跑」，而 HANDOFF.md 2.4 节的误判表明确写着 Xaero 小地图的真实侧别是纯客户端。

修正后的规则（src/sources/modrinth.py::side_from_project）：

Modrinth 字段 判定
server=unsupported client
client=unsupported server
client=required + server=optional client（服务端可不装）
server=required + client=optional both（保守：客户端「可选」不等于不需要）
required+required / optional+optional both
两侧都 unknown 不采信（否则会把作者没填的全判成双端，掩盖真正的不确定）

mcmod 侧同理：客户端需装, 服务端可选 -> client；客户端可选, 服务端需装 -> both。

坑 3：HANDOFF.md 2.1 表格里「锂」与「铷」的 classId 都是 36

同一个 classId 不可能对应两个 mod，这是笔误。不要把那张表直接当准确率基准集， 里面的「运行环境」是 mcmod 的字段原值，不等于人工确认的真实侧别。

坑 4：displayTest 与 mixin 特征不可判单侧

  • displayTest="IGNORE_ALL_VERSION"：纯客户端和纯服务端都可能这么写，判不了；
  • mixin 配置只有 client 段：Xaero 小地图（纯客户端）和一批双端 mod 都这样， 凭它判 client 会让服务端缺 mod（同样崩游戏）。

因此 src/sources/heuristics.py 对这类特征只给 both（low）+ 提示文字， 不产出单侧判定。

六、如何调参 / 扩展

想做的事 改哪里
加第三数据源（如 CurseForge） 在 src/sources/ 加模块，产出 SideVerdict；在 detector.PRIMARY_SOURCES 里登记权重
调整冲突策略 src/detector.py::merge_verdicts()
调整 mcmod 文案映射 src/sources/mcmod.py::parse_run_env()，改完必须补 tests/test_core.py 的用例
调整缓存有效期 config.json 的 cache_ttl_hours（<=0 表示不过期）
关闭某个源 config.json 的 use_mcmod / use_modrinth / use_heuristics，或 CLI 的 --no-mcmod 等

改判定规则前先读 HANDOFF.md 第九节的红线。
